# Q16 · GPT(아스트라) 결과 · 성우 김디도

> 실행 기록 머리(그대로 옮김):
> ```
> model: gpt-6-astra
> reasoning effort: high
> sandbox: read-only
> session id: 01a11233-3366-7340-a5b7-7a7281a4ea60
> ```
> 날짜: 2026-10-05 · 실행: 팀장이 `codex exec`로 돌림 · 아래는 GPT 답 원문(손대지 않음). 본문의 "모델 줄을 옮기지 못했다"는 말은 GPT가 자기 실행 기록을 볼 수 없어서이며, 위 머리가 실제 기록이에요.

**성우 김디도 · Q16 답변이에요.**

**추천은 ‘원문에서 숫자 구간을 찾기 → 문맥·유효성으로 분류하기 → 읽기 생성하기’로 점진적으로 바꾸는 안이에요.** 기존 숫자 변환 함수는 재사용하고, 규칙의 우선순위와 적용 근거를 데이터로 관리해요. 정규식은 구간을 찾는 도구로 계속 써도 돼요.

파일은 수정하지 않았어요. 현재 실행의 `model:`·`reasoning effort:`·`sandbox:` 로그 원문은 제공되지 않아 그대로 옮기지 못했어요. 과거 리뷰의 실행 기록으로 대신하지 않았어요.

**먼저, 현재 코드에서 확인한 사실이에요.**

실제 시험 경로는 `apps/dido-assistant/tests/test_korean_numbers.py`예요. 직접 실행한 결과 **시험 메서드 13개 모두 통과**, G15 원문의 정답 열과는 **30문장 중 29문장 일치**였어요. 21번은 원문 유지 상태이고, 시험에서도 승인되지 않은 차이로 따로 관리하고 있어요(`:90`, `:117`).

현재 `korean_numbers.py`에는 순서대로 적용하는 규칙이 29개 있어요. 이미 시각·점수 문맥 판단(`:122`), 버전 우선 처리(`:183`), 보존 구간 보호(`:112`)가 들어 있어요. 따라서 “문맥을 전혀 보지 않는 코드”라는 평가는 맞지 않아요. 문제는 **분류·검증·읽기·보존 처리가 순차 문자열 치환 안에 섞여 있다는 점**이에요(`:245`).

다음은 이번에 직접 실행한 결과예요. 오른쪽 개선 방향은 제안이며, 낭독 표현의 선택은 **추측**이에요.

| 입력 | 현재 출력 — 실행 확인 | 개선 방향 — 제안 |
|---|---|---|
| `3:10은 경기 점수예요.` | `세 시 십 분은 경기 점수예요.` | 뒤쪽 문맥도 보고 `삼 대 십`을 선택해요. |
| `버전은 2026.10.06이에요.` | `버전은 이천이십육 년 시월 육 일이에요.` | 조사까지 고려해 버전으로 분류하고, 기존 버전 정책대로 각 부분을 읽어요. |
| `2026-02-31` | `이천이십육 년 이월 삼십일 일` | 달력상 유효성을 검사하고, 잘못된 날짜는 원문과 확인 필요 상태를 반환해요. |
| `10000000000000000.5원` | `10000000000000000.오 원` | 미지원 금액 구간 전체를 보존해요. 일부만 바꾸지 않아요. |

반면 `범위는 20-10개예요.`와 `10000000000000000/2`는 현재 원문을 보존했어요. 과거 리뷰의 반례가 모두 그대로 남았다고 주장하지 않아요.

**선택지별 장단점과 의견이에요.**

아래 장단점은 코드·공개 자료를 바탕으로 한 설계 판단이에요. 새 구조의 정확도·속도·개발 기간은 실측하지 않았으므로 효과 예상은 **추측**이에요.

| 번호 | 안건 | 의견(동의·반대·보완) | 근거 | 제안 |
|---|---|---|---|---|
| 1 | 반례마다 정규식 추가 | **단기 보완에는 동의하고, 장기 주력 방식에는 반대해요.** | **장점:** 작은 수정으로 알려진 오류를 고치고, 외부 의존 없이 재현하기 쉬워요. **단점:** 규칙 순서와 부분 치환의 영향을 함께 추적해야 해요. 현재도 뒤 문맥·조사 변형·실패 구간 재치환 반례가 있어요. | 급한 오류 수정에는 쓰되, 새 규칙마다 충돌하는 유형의 반대 예제도 추가해요. |
| 2 | 구간별 문맥 분류 후 읽기 생성 | **추천해요.** | **장점:** 잘못 분류했는지, 숫자를 잘못 읽었는지 따로 확인할 수 있어요. 원문·자리수·미지원 구간을 보존하기 쉬워요. **단점:** 구간 경계와 분류 충돌을 설계해야 하고, 문맥만으로 결정할 수 없는 입력은 여전히 남아요. | 시각·점수·날짜·버전부터 분리하고 기존 `sino`, `native`, `decimal`을 재사용해요. |
| 3 | 규칙표·우선순위 데이터화 | **2번과 함께 추천해요.** | **장점:** 규칙 ID, 우선순위, 적용 조건, 예제, 근거를 함께 검토할 수 있어요. **단점:** 지금의 순차 치환을 표로 옮기는 것만으로 충돌이 해결되지는 않아요. 복잡한 조건을 데이터 문법으로 만들면 별도 언어를 유지하는 부담도 생겨요. | 단위·단서·우선순위는 데이터로, 달력 검사와 읽기 함수는 코드로 유지해요. |
| 4 | 기존 한국어 TN 라이브러리·WFST 사용 | **동일 시험으로 비교한 뒤 결정해요.** | **장점:** 공개 규칙과 분류·읽기 분리 구조를 활용할 수 있어요. **단점:** 우리 읽기 정책과 차이가 있고, 설치·버전·라이선스 관리가 추가돼요. 라이브러리도 규칙 기반이면 같은 종류의 모호성이 남아요. | 곧바로 교체하지 말고 동일 입력에 대한 차이 보고부터 만들어요. |
| 5 | 합성 엔진의 SSML `say-as`에 맡기기 | **선택 가능한 출력 방식으로 보완해요.** | **장점:** 엔진에 숫자의 유형을 명시할 수 있어요. **단점:** 어떤 구간이 시각·번호인지 정하는 일은 여전히 필요해요. 한국어·음성·엔진별 지원과 읽기 차이를 확인해야 해요. | 공통 분류 결과를 지원 엔진에서는 SSML로, 그 밖에서는 한글 읽기로 전달해요. |

| 7 | 입력 단계에서 유형·읽기 지정 | **구조화된 입력에 추천해요.** | **장점:** 일정의 시각, 가격표의 금액처럼 이미 아는 정보를 다시 추측하지 않아도 돼요. **단점:** 자유 문장에는 적용 범위가 제한되고, 지정 자체가 틀릴 수도 있어요. | 입력이 제공한 유형을 우선하되 형식·값을 검증해요. 대본에는 구간별 읽기 수정 기능을 둘 수 있어요. |

SSML의 유형 지정 역할은 [규격 문서](https://www.w3.org/TR/speech-synthesis11/#S3.1.9)에서, 한국어를 포함한 유형 지원 사례는 [공식 발음 제어 문서](https://learn.microsoft.com/ko-kr/azure/ai-services/speech-service/speech-synthesis-markup-pronunciation)에서 확인했어요. **현재 연결된 합성 엔진에서 그대로 작동하는지는 확인하지 않았어요.**

**바꿀 구조는 문장 전체가 아니라 숫자 구간별로 분류해야 해요.**

한 문장에 시각·금액·버전이 함께 나올 수 있어요. 다음처럼 처리하는 안을 제안해요.

1. **원문과 위치를 보존해요.** 숫자·구분자·단위를 묶고, 앞뒤 문맥을 원문에서 읽어요. 먼저 변환된 문장이 다음 판단의 근거가 되지 않게 해요.
2. **해석 후보를 만들어요.** `3:10`에는 시각·점수·비율 후보가 있을 수 있어요. 유효한 시각이라는 사실만으로 시각이라고 확정하지 않아요.
3. **명시적 유형, 문맥, 형식 검증을 함께 적용해요.** 날짜는 달력 검사까지 하고, 단서가 충돌하면 보류해요. 긴 구간이라는 이유만으로 무조건 우선하지 않아요.
4. **확정된 구간을 한 번만 읽기로 바꿔요.** 보류·미지원 구간은 전체를 보존하고 상태와 이유를 남겨요. 문자열 속 특수 문자로 숨기는 대신 구간 객체로 관리해요.
5. **읽기와 쉼 지시를 구분해요.** 숫자를 올바르게 풀었다고 억양·끊어 읽기까지 좋아졌다고 판단하지 않아요.

구간에는 최소한 `원문 위치·원문·유형·읽기·적용 규칙 ID·상태`를 남기는 편이 좋아요. 번호와 소수는 선행 영·소수 끝의 영이 중요하므로 원문 자리수를 유지해요. 분류 단계에서 모든 숫자를 정수나 부동소수점으로 바꾸지 않아요.

기존 `normalize(text) → str` 인터페이스는 유지하고, 내부에 상세 결과를 반환하는 함수를 추가하면 호출부 변경을 줄일 수 있어요. **원문 보존은 처리 성공과 구별해야 해요.** 원문을 합성기에 보내도 어떻게 읽을지는 별도 문제예요.

**기존 시험을 지키는 이행 방법이에요.**

| 단계 | 지킬 방법 |
|---|---|
| 기준 고정 | 현재 코드 버전, 기존 시험의 입력·기대값, G15 원문 30문장과 잠정 허용안을 고정해요. 새 구현의 출력을 정답으로 자동 갱신하지 않아요. |
| 두 기준 분리 | **현재 동작 보존 시험**과 **목표 읽기 시험**을 나눠요. G15 21번은 현재 동작이 맞아도 목표 정답과는 불일치라고 계속 보고해요. |
| 구조 변경부터 | 먼저 출력이 같도록 구조만 바꿔요. 현재 시험은 문맥 없는 `3:10`을 시각으로 기대하므로, 이를 보류로 바꾸는 정책 변경은 별도 변경으로 다뤄요. |
| 차이 보고 | `문항 ID / 원문 / 기존 출력 / 새 출력 / 목표·허용안 / 유형·규칙 / 변경 이유`를 나란히 보여 줘요. 띄어쓰기 차이, 읽기 선택 차이, 수치·자리수 손실을 구별해요. |
| 반례 확장 | 앞·뒤 문맥, 조사, 여러 공백·탭, 문장 경계, 같은 문장 속 여러 유형을 검사해요. 잘못된 날짜·큰 수·부분 변환·비숫자 구간 훼손도 포함해요. |
| 판정 후 전환 | 승인된 변경 외 기존 기대값 차이는 없어야 해요. G15는 **29 일치·1 미해결**을 숨기지 않아요. 새 반례는 목표대로 처리해야 하고, 그 뒤 실제 음성으로 숫자 정확성·쉼·억양을 따로 들어봐요. |

G15에는 **추측으로 표시된 잠정 읽기**도 있어요. 문자열 불일치를 모두 오독으로 세면 안 되지만, 허용안을 개발자가 임의로 넓혀 시험을 통과시켜서도 안 돼요. 같은 문장의 공백 변형을 새 독립 문장처럼 집계하지 않고, 별도의 새 문장 묶음도 남겨 두는 편이 좋아요.
