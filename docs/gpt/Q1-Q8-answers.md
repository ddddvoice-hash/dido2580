## Q1 채용 담당자가 먼저 보는 3가지는 무엇이고, 우리 대표작에는 무엇이 빠졌나요?

채용 담당자 모두에게 통하는 순위는 **모르겠어요**. 다만 이 직무와 현재 자료를 기준으로 다음 세 가지를 먼저 보여 주는 구성을 제안해요.

| 먼저 보여 줄 것 | 현재 확인한 것 | 부족한 것 |
|---|---|---|
| **어떤 문제를 판단하고 해결했는지** | 따뜻함을 5항목과 8개 감점으로 구체화했어요. | 실제로 판단이 어려웠던 답변 하나와, 근거를 검토해 결론을 낸 사례가 필요해요. |
| **결과를 얼마나 믿을 수 있는지** | 계산·일치도 도구와 테스트가 있어요. | 독립적인 사람 평가, 항목별 α와 불확실성, 실패 사례가 필요해요. |
| **본인이 무엇을 결정했는지** | 작업·검토 기록이 있어요. | 성우 김디도가 정한 기준, 받아들인 지적, 반려한 제안을 한 사례로 연결해야 해요. |

우선 추가할 결과물은 **“답변 → 독립 채점 → 불일치 근거 → 기준 수정 제안 → 남은 한계”를 보여 주는 사례 한 장**이에요. 도구 기능을 더 늘리는 것보다 우선할 만해요.

## Q2 평가자 2~3명일 때 답변 몇 개로 α를 말할 수 있나요? 신뢰구간도 필요한가요?

**정직하게 보고할 수 있는 표본 수와, 정밀하게 추정할 수 있는 표본 수는 달라요.** “몇 개 이상이면 믿을 만하다”는 공통 최소치는 없어요. 점수 분포·불일치 정도·결측·문항 간 관련성에 따라 달라져요.

현재 상황에는 다음 순서를 제안해요.

| 단계 | 제안 규모 | 말할 수 있는 범위 |
|---|---|---|
| 기준 이해와 절차 점검 | 10상황 × 3답변, 평가자 2~3명 | 예비 실험이에요. 어디서 판정이 갈리는지 찾아요. |
| 공개할 첫 탐색 결과 | 비위기 20상황 × 3답변, 가능하면 평가자 3명 | 이 답변 묶음과 평가자 집단에서 관찰한 일치도예요. |
| 더 정밀한 결과 | 예비 자료의 분포로 필요한 상황 수를 다시 설계해요. | 목표 신뢰구간 폭을 먼저 정한 뒤 표본을 늘려요. |

위 규모는 **실무 제안이며 통계적 최소치가 아니에요**. 위기 문항은 높은 점수를 의도한 안전한 답변만 별도로 평가하고, 실제 답변 수와 구성을 보고해요. 의도한 점수는 평가자에게 숨겨요. 좋음·나쁨이 뚜렷한 답변만 고르면 경계 답변에서의 어려움이 가려질 수 있어요.

공개 결과에는 다음을 함께 보여 주세요.

- 항목별 **서열 α와 95% 신뢰구간**, 같은 점수 비율, 점수 분포를 적어요.
- 같은 상황의 답변 3개는 관련되어 있으므로, **상황 단위로 묶어 재추출하는 부트스트랩**을 제안해요. 선택된 상황의 모든 답변과 평가자 점수를 함께 가져와요.
- 예를 들어 5,000회 재추출하되, 계산 불가가 나온 횟수·난수 시드·계산 방법도 남겨요. 적은 상황 수를 부트스트랩으로 보충할 수는 없어요.
- 평가자 수, 항목별 유효 답변 수, 제외·건너뛰기 수, 답변 출처, 기준표 버전을 밝혀요. 평가자 2~3명을 고정한 구간은 새로운 평가자 집단의 변동까지 충분히 반영하지 못해요.

**현재 전후 비교 설계에는 보완이 필요해요.** 새 문항으로 바꾸면 기억 효과는 줄지만 문항 난이도도 바뀌어요. 따라서 α 상승을 곧바로 “기준 수정 효과”라고 부를 수 없어요. 먼저는 **“서로 다른 두 회차의 탐색 결과”**라고 보고하세요. 효과를 더 분리하려면 기준을 다듬는 데 쓰지 않은 공통 검증 답변과, 구·신 기준표의 적용 순서를 나누는 설계가 필요해요.

또한 α는 **평가자끼리의 일치도이지 정답률이나 안전성 인증이 아니에요**. 모두 같은 점수만 주면 관찰 일치는 100%일 수 있지만 α는 계산되지 않아요. 이를 “일치가 아니다”라고 설명하면 부정확해요.

**근거:** `docs/eval/calibration.md`, [일치도 계산 코드](C:/Users/ddddv/dido2580/apps/warmth-scorer/app.js:177), [KALPHA 설명 자료](https://www.afhayes.com/public/kalpha.pdf), [α 부트스트랩 설명 자료](https://www.afhayes.com/public/alphaboot.pdf). 상황 단위 재추출은 현재 자료 구조에 맞춘 통계 설계 제안이에요. 현재 앱에서는 신뢰구간 계산 기능을 확인하지 못했어요.

**확실도:** 계산·해석상의 구분은 **확실**, 제안 규모와 재추출 설계의 실무 적합성은 **추측**, 목표 정밀도에 필요한 정확한 표본 수는 **모름**이에요.

## Q3 위기 문항 평가자의 정서 부담을 어떻게 줄일까요?

현재의 사전 안내·회차당 위기 문항 제한·건너뛰기 허용에 **평가자가 노출과 중단을 통제하는 절차**를 더하면 좋겠어요.

1. **시작 전에 범위를 알려요.** 다룰 주제와 예상 분량을 안내하고, 해당 묶음의 참여 여부를 따로 선택하게 해요. 개인 경험이나 진단을 밝히게 하지 않아요.
2. **열어 보기 전 선택권을 줘요.** 민감한 본문과 음성을 자동으로 표시·재생하지 않고, 건너뛰기·중단·일반 문항 전환을 쉽게 해요.
3. **문항 수뿐 아니라 실제 노출량을 관리해요.** 위기 1문항도 답변 여러 개를 읽고 다시 검토하면 노출이 늘어요. 답변 수·반복 열람·작업 시간을 함께 봐요. `risk` 표시뿐 아니라 실제 내용도 확인해요.
4. **휴식과 중단에 불이익을 주지 않아요.** 예비 운영은 20분 작업 뒤 5분 휴식처럼 짧게 시작할 수 있지만, 이를 검증된 안전 기준이라고 부르지는 않아요. 보상이 있다면 휴식과 중단 때문에 불이익을 받지 않도록 해요.
5. **마무리 대화는 선택 사항으로 해요.** 힘든 내용을 다시 자세히 이야기하도록 요구하지 않아요. 쉬기·종료하기·도움 요청하기 중 선택하게 해요.
6. **실제 위기 표현을 만나면 채점을 멈추는 담당 절차를 정해요.** 평가자가 혼자 대응 책임을 지지 않도록 운영 담당자와 연결 경로를 미리 정해요.

건너뛰기는 0점으로 넣지 않아요. 해당 항목에 평가가 두 개 이상 남으면 계산에 쓰일 수 있고, 부족하면 제외돼요. 제외 수와 범주를 보고하되 개인의 중단 사유는 공개하지 않아요.

**근거:** `docs/eval/calibration.md`, `docs/eval/scenarios-v0.json`, `app.js`의 결측 처리. 유해 자료 노출과 지원 필요성은 [Emotional Toll and Coping Strategies](https://aclanthology.org/2024.legal-1.10/)를 참고했어요. 해당 문헌은 다른 종류의 유해 자료를 다루므로, 우리 위기 문항에 대한 효과를 직접 검증한 근거는 아니에요.

**확실도:** 현재 운영 규칙과 계산 동작은 **확실**, 추가 운영안의 효과는 **추측**, 모든 평가자에게 안전한 노출 시간은 **모름**이에요.

## Q4 목소리 측정값과 따뜻함 판정의 관계를 보려면 녹음이 최소 몇 개 필요한가요?

**현재 정보만으로 통계적 최소 녹음 수를 정할 수는 없어요.** 먼저 “차이를 보여 주는 시연”과 “관계를 추정하는 연구”를 나누는 게 좋아요.

- **시연:** 현재 계획의 5문장 × 2방식 = **10개 녹음**이면 사례 비교는 가능해요. 일반적인 상관관계를 주장하기에는 부족해요.
- **첫 탐색 실험 제안:** **20문장 × 2방식 = 40개 녹음**, 평가자 **3~5명**으로 시작해요. 이것도 검정력으로 산출한 최소치가 아니에요.

탐색 실험은 이렇게 설계해요.

1. 같은 문장을 같은 화자·마이크·거리·녹음 설정으로 두 방식씩 녹음해요. 녹음 순서는 섞어요.
2. 듣는 사람에게 방식 이름과 측정값을 숨기고, 재생 순서를 무작위로 제시해요.
3. 상황과 함께 듣고 **따뜻하게 들리는 정도·내용에 맞는 정도·이해하기 쉬운 정도**를 구분해 평가해요. 한 가지 질문으로 모두 대신하지 않아요.
4. 음절 수와 문장 경계는 사람이 확인한 값으로 자동 추정값을 점검해요. 특히 긴 쉼이 반드시 문장 끝은 아니에요.
5. 문장별로 측정값 변화와 사람 판정 변화를 비교해요. 40개를 독립 표본 40개로 취급하지 않고 **20개 문장 쌍**이라는 구조를 반영해요.
6. 여러 특성을 동시에 바꿨다면 “낭독 방식에 따른 차이”라고 해석해요. 속도 하나의 효과를 말하려면 다른 특성을 가능한 한 유지한 별도 실험이 필요해요.

성우 김디도 한 화자의 결과는 해당 화자·문장·청취 조건의 결과예요. 다른 화자나 합성음으로 일반화하려면 화자와 음성 종류를 늘려야 해요. 특정 음높이나 내림 비율을 따뜻함의 정답으로 쓰면 안 돼요.

**근거:** [목소리 측정 근거표](C:/Users/ddddv/dido2580/docs/eval/voice-evidence.md), [시연 문장](C:/Users/ddddv/dido2580/voice/test-sentences.csv), 반복측정에 관한 일반 통계 지식이에요. [How Do You Say ‘Hello’?](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0090779)는 목소리와 인상 평가의 관계를 연구하지만, 한국어 상담 문장에 보편적인 따뜻함 기준을 제공하지는 않아요.

**확실도:** 현재 계획과 추정 방법의 한계는 **확실**, 40개 녹음 운영안은 **추측**, 통계적으로 필요한 최소치는 **모름**이에요.

## Q5 공개할 때 문항·기준표·코드의 라이선스는 어떻게 정할까요?

**자료별 적용 범위를 나눠 명시하는 방안**을 제안해요.

| 대상 | 제안 | 확인할 점 |
|---|---|---|
| 직접 만든 상황 문항·설명 문서 | **CC BY 4.0** 검토 | 상업적 이용과 수정·재배포도 허용해요. 출처·라이선스·변경 표시가 필요해요. |
| 기준표 | 외부 수정판도 허용하려면 **CC BY 4.0** 검토 | 저장소 원본을 대표만 수정한다는 운영 규칙과 외부 이용자의 수정 권리는 별개예요. 수정판을 공식 원본으로 오인하지 않도록 버전과 변경 사항을 구분해요. |
| 직접 작성한 코드 | **MIT** 검토 | 배포할 때 저작권·허가 고지를 보존해요. 외부에서 가져온 코드의 조건은 따로 확인해요. |

CC BY 4.0은 수정 허용을 포함하므로, **“배포는 자유지만 기준표 수정은 누구에게도 허용하지 않는다”는 조건과 함께 설명하면 모순**이에요. 수정판 배포까지 막고 싶다면 CC BY-ND 4.0 같은 다른 선택을 검토해야 하고, 재사용 범위가 줄어드는 점을 받아들여야 해요. 조건을 지킨 이용자에게 이미 준 허락을 임의로 철회할 수 없다는 점도 중요해요. [CC BY 4.0 설명](https://creativecommons.org/licenses/by/4.0/deed.ko), [라이선스 FAQ](https://creativecommons.org/faq/), [MIT 원문](https://opensource.org/license/mit)

현재 [pyproject.toml](C:/Users/ddddv/dido2580/pyproject.toml:11)에는 MIT 표시가 있지만, 별도 패키지의 메타데이터예요. 이것만으로 평가 키트 전체의 라이선스가 확정됐다고 단정하지 않겠어요.

공개 전에는 다음도 정리해야 해요.

- 외부 문항·서비스 답변·번역문은 출처와 재배포 조건을 개별 확인해요. **논문·코드·데이터의 라이선스가 같다고 가정하지 않아요.**
- AI가 작성한 부분과 사람이 검토·수정한 부분을 구분해요. 개별 결과물의 저작권 성립 여부는 여기서 판단할 수 없어요.
- 평가는 익명 코드로 공개하고, 녹음 원본은 저장소에 올리지 않는 현재 규칙을 유지해요.
- 자료 이용 허락이 목소리 복제나 **성우 김디도**의 공식 보증을 뜻하지 않는다고 구분해요.
- 문항은 평가용이며 임상 검증 자료나 안전 인증이 아니라는 범위를 밝혀요.

**근거:** `AGENTS.md`, `docs/FLAGSHIP.md`, `pyproject.toml`, 위 라이선스 원문이에요.

**확실도:** 인용한 라이선스의 기본 조건과 저장소 표기는 **확실**, 권장 조합은 **추측**, 개별 자료의 권리관계와 법적 판단은 **모름**이에요.

## Q6 비교할 공개 평가 자료와 우리 차별점은 무엇인가요?

먼저 다음 네 자료의 **평가 범위와 실패 유형**을 비교하면 좋아요. 전부 실행하거나 원문 문항을 가져올 필요는 없어요.

| 자료 | 비교할 부분 | 우리 키트에서 보완할 부분 |
|---|---|---|
| [EmpatheticDialogues](https://arxiv.org/abs/1811.00207) | 감정이 담긴 상황에서 공감적인 대화를 평가해요. | 공감 표현과 사실성·절제·다음 행동을 어떻게 구분하는지 비교해요. |
| [ESConv](https://arxiv.org/abs/2106.01144) | 정서 지원 전략과 여러 차례 이어지는 대화를 다뤄요. | 현재 단일 답변 평가가 앞선 대화와 사용자의 반응을 놓치는지 살펴봐요. |
| [WildGuardTest](https://arxiv.org/abs/2406.18495) | 요청·답변의 유해성과 답변의 거절 여부를 구분해요. | 안전 신호를 놓치는 문제와, 적절한 답변 여부를 분리해 봐요. |
| [XSTest](https://aclanthology.org/2024.naacl-long.301/) | 안전한 요청까지 지나치게 거절하는 현상을 시험해요. | 민감한 낱말만 보고 안전한 도움까지 막는 사례가 빠졌는지 확인해요. |

우리의 차별점으로 제시할 만한 것은 **한국어 상황, 근거 문장에 연결한 5항목·8감점, 목소리 판단 근거, 키보드 중심 채점, 평가자 불일치 검토를 한 흐름으로 묶었다는 점**이에요.

다만 **“유일하다”, “기존 자료보다 우수하다”, “안전성을 검증했다”는 주장은 아직 근거가 없어요.** 특히 목소리 측정과 사람 판정의 연결은 앞으로 실증할 부분이에요. 번역한 자료의 점수를 원래 자료 점수와 직접 비교해서도 안 돼요.

재사용 조건도 확인해야 해요. 예를 들어 ESConv의 [배포 안내](https://github.com/thu-coai/Emotional-Support-Conversation/blob/main/README.md)는 학술 연구 용도로 제한해요. 공개돼 있다는 이유로 포트폴리오에 원문을 재배포해도 된다고 가정하면 안 돼요.

**근거:** 위 자료의 원 논문·배포 안내, `rubric.json`, `scenarios-v0.json`, `docs/FLAGSHIP.md`예요.

**확실도:** 자료별 목적과 현재 구현 범위는 **확실**, 차별점이 채용에서 가질 효과는 **추측**, 상대적인 성능 우위는 **모름**이에요.

## Q7 3분 시연 영상은 어떻게 구성할까요?

**현재 확인된 기능과 아직 남은 검증을 함께 보여 주는 180초 구성**을 제안해요. 발화 사이 시간에는 실제 조작·화면 읽기·결과 확인을 넣어요.

| 시간 | 화면 | 말할 문장 |
|---|---|---|
| 0:00–0:20 | **성우 김디도** 제목과 기준표 예시 A·C | “다정하게 들리는 답변이 실제로 도움이 되는 답변일까요? 이 평가 키트는 점수마다 답변 속 근거를 남기도록 만들었어요.” |
| 0:20–0:45 | 예시 A=0·B=4·C=10과 감점 근거 | “기준표에 들어 있는 예시예요. 좋은 결과를 장담하거나 의존을 유도하는 표현은 감점해요. 이 숫자는 실제 서비스 비교 결과가 아니에요.” |
| 0:45–1:15 | 키보드로 항목 선택·점수 입력·근거 저장 | “다섯 항목을 따로 보고, 이렇게 근거 문장을 남겨요. 어떤 표현 때문에 판단했는지 다시 검토할 수 있어요.” |
| 1:15–1:40 | JSONL 내보내기와 기록 구조 | “기록에는 점수와 근거, 기준표 버전이 함께 남아요. 공개 자료에서는 평가자를 익명 코드로 구분해요.” |
| 1:40–2:05 | 일치도 기능과 ‘사람 평가 결과 준비 중’ 표시 | “같은 답변을 독립적으로 채점한 뒤 판정이 갈리는 곳을 찾는 기능이에요. 실제 사람 평가 결과와 신뢰구간은 아직 준비 중이에요.” |
| 2:05–2:35 | 목소리 근거표와 동일 문장 두 방식의 비교 계획 | “목소리는 속도와 쉼 같은 측정값을 사람의 판단 근거와 연결하려고 해요. 측정값만으로 따뜻함 점수를 정하지 않아요. 녹음 비교는 다음 검증 단계예요.” |
| 2:35–3:00 | 확인한 것·남은 것·성우 김디도의 역할 | “현재 확인한 것은 계산과 자료 구조예요. 다음에는 독립 평가자의 불일치와 녹음 비교를 확인할 거예요. 성우 김디도가 정한 기준과 그 근거를 검토할 수 있도록 보여 드릴게요.” |

실제 평가나 녹음이 완료되면 해당 장면을 **실측 결과와 한계**로 교체해요. 시연 영상에는 자막을 넣고, 공개 화면에서 개인 식별 정보가 보이지 않도록 해요. 녹음 비교 장면의 공개는 기존 녹음 비공개 규칙과 공개 범위를 먼저 맞춰야 해요.

**근거:** `docs/FLAGSHIP.md`, `apps/warmth-scorer/GPT_PROMPT.md`, `app.js`, `docs/eval/voice-evidence.md`. A·B·C 계산은 이번 실행에서 확인했어요. 브라우저 조작 장면은 이번 실행에서 확인하지 않았어요.

**확실도:** 계산값과 계획 상태는 **확실**, 영상 구성과 전달 효과는 **추측**이에요.

## Q8 지금 계획에서 무엇을 덜어내야 하나요?

**기능·문항·소개 문구의 확장보다 실제 평가 사례 하나를 완성하는 데 집중하는 편을 제안해요.**

| 덜어낼 것 | 이유 | 남길 것 |
|---|---|---|
| 첫 화면에서 구성 A~F를 모두 설명하기 | 무엇을 잘하는지 파악하기 전에 설명 부담이 커질 수 있어요. | 문제 하나, 실제 조작 하나, 근거 하나를 앞에 둬요. |
| 사람 평가 전에 문항 수를 계속 늘리기 | 60개가 있다는 사실만으로 평가 품질이 검증되지는 않아요. | 기존 문항 중 사용할 묶음을 고르고 실제 채점해요. |
| 독점성·시장 전체에 관한 강한 주장 | “유일함”이나 시장의 보편적 부족을 뒷받침할 자료가 없어요. | 확인한 구현과 검증 범위만 말해요. |
| AI 팀 구성과 검토 건수를 전면에 내세우기 | 검토 건수는 사용자에게 생긴 개선을 직접 보여 주지 못해요. | 중요한 지적 하나와 그에 따른 결정·수정 결과를 보여 줘요. |
| α 한 숫자나 상승 화살표로 성과 요약하기 | 문항 구성·평가자·불확실성을 가리고 타당성과 혼동될 수 있어요. | 항목별 결과, 불일치 사례, 신뢰구간을 남겨요. |
| 음높이·쉼의 기준값을 이상적인 따뜻함처럼 제시하기 | 한 화자의 참고값을 보편적 정답으로 오해할 수 있어요. | 같은 문장의 비교와 측정이 설명하지 못한 사례를 남겨요. |

자료 사이의 상태 불일치도 줄여야 해요. 예를 들어 `FLAGSHIP.md`의 상황 문항 상태는 “없음”인데 실제로 60개 초안이 있어요. 이런 불일치는 기능 부족보다 결과물의 관리 상태를 의심하게 할 수 있어요.

첫 공개 묶음은 **소개 한 페이지·3분 시연·독립 채점 사례 한 묶음·재현 안내·한계 설명** 정도로 좁히면 좋겠어요. 실제 결과가 확보되기 전에는 α 개선이나 목소리 타당성을 완성된 성과로 내세우지 않아요.
