# 목소리 관찰 근거표 (대표작 B) v3.1 · 성우 김디도

2026-10-06 · **v3.1**: GPT 아스트라 R17(R15 대조 16건 + 녹음 전 확정 표 10건) 반영. 2026-10-05 · **v3**: GPT 아스트라(`gpt-6-astra`) R15 비판(R10 대조 12건 + 추가 4건)을 반영해 클라우드 팀장이 고침. v2는 R10 12건과 G4 독립 초안을 반영한 판이었어요.
측정 방법의 자세한 설명은 G4(`docs/gpt/G4-voice-evidence.md`)를 기준으로 삼았어요. R15의 코드 지적은 클라우드가 `apps/voice-check/profile.js`(145~235줄)와 `apps/reading-coach/analysis.js`(75~92줄)에서 직접 다시 확인했어요.

## 원칙

1. **측정값은 근거이지 판정이 아니에요.** 따뜻한지는 사람이 기준표로 판단하고, 측정값은 그 판단 옆에 놓는 관찰 기록이에요. 점수로 바꾸지 않아요. 측정값과 사람의 판단 이유는 서로 다른 칸에 적어요.
2. **목표값이 없어요.** 어떤 빠르기·쉼·음높이가 "맞다"고 정하지 않아요. 한국어 상담 문장에서 그런 값을 입증한 자료를 확인하지 못했어요. 아래 "함께 들을 질문"도 검증된 법칙이 아니라 듣는 사람을 돕는 제안이에요.
3. **측정 불가는 측정 불가예요.** 세 경우를 구별해 그대로 적어요. 0점이나 "따뜻하지 않음"으로 바꾸지 않아요.
   - 정상 결과인데 값이 없음: 쉼 0개, 말끝 후보 0개, `null`
   - 일부 제외: `skipped`(유효 음높이가 모자라 뺀 덩어리 수)
   - 파일 전체 분석 실패: `profile.js`는 말소리를 못 찾으면 결과 대신 오류를 내고, `analysis.analyze()`는 `failed: true`와 이유(`threshold`: 조용한 부분이 모자라 기준을 못 잡음, `no_speech`: 말소리 없음)를 돌려줘요(매니저 A9, R17 반영). 이때 시각·길이·쉼 개수의 0은 **측정값이 아니에요.** 오류 문구를 그대로 기록하고 그 녹음의 수치 비교는 보류해요.
4. **사람이 먼저 듣고, 수치는 나중에 봐요.** 수치를 먼저 보면 판단이 끌려갈 수 있어요(가능성, 확인 안 됨).

## 항목: 재는 것과 못 재는 것

| 기준표 항목 | 이 도구가 재는 것 (실제 필드) | 함께 들을 질문 | 못 재는 것 |
|---|---|---|---|
| `pace` 빠르기 | `syllables.perSecSpoken`: 음절 수 **추정**(크기 봉우리) ÷ 검출된 말소리 시간 합. `perSecTotal`: 같은 추정 ÷ 파일 전체 길이 | 이 상황에서 듣는 사람이 따라올 수 있었나 | 실제 음절 수. **검출된 말소리 구간과 음절 추정이 같다면, 쉼이 길어져도 `perSecSpoken`은 그대로**예요(분모에 쉼이 없음). 검출 기준은 파일 전체에 따라 달라지므로 구간이 늘 같다는 보장은 없어요. 그래서 빠르기는 아래 쉼·발화 길이와 꼭 함께 봐요 |
| `pause` 쉼 | `pauses`: 260ms 이상 쉼의 개수·분당 횟수·길이 분포. 개별 쉼의 시각은 프로필 요약에 없고, `analysis.analyze().pauses[].time`(쉼의 **가운데** 시각)과 `length`로 따로 얻어요 | 중요한 말 앞에서 쉬었나(원고와 맞춰 사람이 확인) | 어느 낱말 앞의 쉼인지. 쉼 시작·끝은 가운데 시각과 길이로 계산하거나 사람이 표시해요 |
| `ending` 말끝 | `sentenceEnd`: 700ms 이상 쉼 앞 덩어리마다 **끝 300ms의 음높이 중간값과 덩어리 전체의 음높이 중간값의 차이**(반음). ±1반음 밖이면 내림/올림. `count`·`skipped`를 함께 적어요 | 문장의 기능과 상황에 맞게 들렸나, 그렇게 들린 구간은 어디인가 | **실제 오르내림의 모양.** 끝 300ms 안에서 올라가도 덩어리 앞부분보다 낮으면 "내림"으로 세요(GPT 합성음 재현: 끝을 120→180Hz로 올려도 앞부분이 240Hz면 −8.2반음 "내림"). 마지막 덩어리는 아예 계산하지 않고 `skipped`에도 들어가지 않아요 |
| `pitch` 음높이 | `pitch`: 유효 F0 중간값(Hz), 10~90 백분위 폭(반음), 유효 프레임 비율 | 단조롭거나 과장되게 들렸나 | 감정, 옥타브 오류가 없는지 |
| (기준표에 없음) 크기 | 전체·말소리 RMS(dBFS), 최대값 | 너무 크거나 작게 들렸나 | 크기의 안정성. 시간별 크기 곡선은 `analysis.js`가 이미 계산하지만, **프로필 요약에는 안정성 지표가 없어요**. dBFS는 파일 값이고 실제 듣는 크기와 달라요 |
| `breath` 호흡·음색 | **재지 않음** | 숨소리·음색이 내용과 어울렸나 | 전부 사람 청취 |
| `congruence` 내용과의 일치 | **재지 않음** | 말투가 말의 내용과 맞았나 | 전부 사람 청취 |

## 상황 문항의 낭독 메모와 잇기

상황 문항(`docs/eval/scenarios-v0.json`)의 낭독 메모는 **낭독 지시**예요. 이 표로 "지시대로 됐다"를 자동 판정하지 않아요. 사람이 들은 판단 옆에 관련 수치를 함께 보여 줄 뿐이에요.

| 낭독 메모 예 | 옆에 놓을 수치 |
|---|---|
| "평소보다 조금 늦추고" | `perSecSpoken`과 함께 **첫~끝 발화 길이(`analysis.analyze().duration`, 파일 전체 길이인 `durationSec`와 다름)·쉼 합계·쉼 길이**. 쉼 때문에 길어진 것과 발음 자체가 느려진 것을 나눠 봐요(같은 원고끼리만 비교) |
| "첫 문장 뒤 짧게 쉬기", "질문 뒤 기다리기" | 해당 시각의 쉼 길이(위치는 사람이 표시) |
| "말끝을 차분히 내리기", "끝을 살짝 올려 열어 두기" | 긴 쉼 앞 끝부분 음높이 차이(실제 궤적은 아님, 마지막 문장은 못 잼) |
| "번호는 또렷하게, 천천히" | 아직 구간 측정이 없음(다음 과제) |

## 비교 시연 설계

같은 문장을 두 방식으로 읽은 녹음으로, 측정 근거와 사람의 청취 판단을 **연결하는 과정**을 보여 줘요. 아래 **녹음 전 확정** 항목이 모두 정해지기 전에는 녹음하지 않아요.

### 녹음 전 확정 (R15·R17 반영 · 대표 확인 필요)

| 정할 것 | 팀장 제안 (대표가 바꿀 수 있음) |
|---|---|
| 문장과 상황 | 원고는 `voice/test-sentences.csv`의 문장 그대로 고정하고 바꾸지 않아요. 각 문장은 상황 문항에 대한 **완결된 답변이 아니라 짧은 발췌**예요. 그래서 상황은 "누구에게 하는 말인지"를 정하는 데만 쓰고, 그 상황의 "꼭 할 일"을 해냈는지는 이 시연에서 판단하지 않아요(R17-1~5).<br>B01→s07 상실 뒤 털어놓기 어려웠던 마음에 감사하는 발췌 · B02→s52 재촉하지 않는 말투의 발췌(사별 뒤 외로움을 알아주는 말은 없음) · B03→s01 숨 돌린 순간을 묻는 질문(허전함 인정은 없음) · B04→s10 지친 마음을 인정하는 발췌("세 번째"는 원고에 없음) · B05→s30 **번호 안내 발췌만**(안전 확인 질문이 없어서 위기 대응 예시로 보여 주지 않아요. "바로 연결할 수 있어요"는 실제 연결 기능이 없으니 공개 전 원고 문구를 대표가 다시 정해요) |
| 두 방식의 녹음 지시 | 두 방식 모두 **같은 상황 문구·같은 상대·같은 원고**를 주고, 연습 횟수(1번)와 추가 코칭(없음)도 같게 해요. 그 위에 방식 1 "평소 안내 낭독", 방식 2 "그 상황의 사람에게 말하듯" 한 줄씩. 상황 파일의 낭독 메모와 빠르기·쉼·음높이 숫자는 주지 않아요 |
| 평가자에게 줄 것 | 두 녹음 모두에 같은 상황 문구와 원고. 방식 지시·CSV "확인할 점"·상황의 낭독 메모는 가려요(R17-10). CSV의 "확인할 점"(예: B04 "약 142Hz 근처")은 목소리 복제 점검용 메모라 평가 기준이 아니에요 |
| 테이크와 고르기 | 문장·방식마다 2테이크를 녹음하고 **둘 다, 녹음 순서와 함께 보존**해요. 첫 테이크를 써요. 첫 테이크를 빼는 사유는 원고 틀림·찢어짐·녹음 중 큰 잡음만이고, 사유·구간·판정자를 **수치를 보기 전에** 적고 선택을 잠가요. 둘 다 못 쓰면 1번만 더 녹음하고, 그래도 안 되면 그 문장은 "보류"로 공개해요. **말소리 검출 실패는 테이크를 바꾸는 사유가 아니에요**(R17-7·8) |
| 녹음 순서 | 문장 순서를 섞고, 문장마다 방식 1/2 순서를 번갈아(AB, BA) 미리 표로 정해요. 5문장마다 쉬어요 |
| 녹음 조건 | 같은 장소·마이크·거리·각도·입력 크기, WAV, 자동 음량·잡음 처리 끔. 처음과 끝 조건을 적어요 |
| 여백과 분석 구간 | 모든 파일에 **같은 규칙**을 써요. 파일마다 결과를 보고 여백을 바꾸지 않아요. 검출 기준이 파일 전체에서 조용한 부분의 비율로 정해져서, 말소리가 길고 여백이 짧으면 실패해요(R17 재현: 10초 소리는 앞뒤 0.5초 여백에서 실패, 1초에서 성공. 클라우드가 같은 결과를 다시 확인). 그래서 **0.3~0.5초는 안전한 범위가 아니에요.** 제안: 앞뒤 여백 각각 1초로 시작하되, 대표의 실제 목소리로 **예비 녹음**(시연에 쓰지 않는 문장)을 먼저 재서 규칙을 확정해요. 검출에 성공해도 시작·끝·내부 쉼 위치를 사람이 파형으로 확인해요. 실패하면(이제 분석 결과에 `failed`가 표시됨, 매니저 A9) 그 테이크를 유지하고 수치 비교만 보류해요 |
| 재생 조건 | 같은 재생 장치·볼륨. 제안: **음량을 맞추지 않고** 녹음된 그대로 재생해요(맞추면 크기 수치를 비교에서 빼야 해서). 대표가 맞추기로 하면 방법과 값을 적어요 |
| 익명 파일명 | 무작위 번호만 써요. 파일명·순서에서 방식이나 테이크가 드러나지 않게 해요 |
| 청취 기록지 | `docs/eval/voice-listening-sheet.md`(GPT G11 채택). 키보드 왼손 `a/s/d/f`로 판단을 적고, 수치 전 첫 판단·수치 뒤 다시 들은 판단·재현 기록을 칸으로 나눠요 |

### 순서

1. **듣기(먼저):** 평가자 2명 이상이 낭독 의도와 수치를 모르는 채로 듣고, 기준표 항목별 판단·이유·구간을 따로 적어요. 문장마다 AB/BA 재생 순서를 미리 정하고, 다시 듣기는 3번까지, 선택지에 "차이 없음"과 "판단 보류"를 넣어요. 이 동안 평가자끼리 이야기하지 않아요.
2. **수치(나중):** **5문장의 첫 판단을 모두 확정한 뒤에** 수치를 한꺼번에 공개해요. 문장마다 공개하면 앞 문장의 수치가 뒤 문장 판단에 영향을 줄 수 있어서예요(가능성). 측정값·단위·검출 실패·`skipped`를 나란히 놓고, 다르게 들린 구간을 다시 들어요. 처음 판단과 다시 들은 판단을 구분해 남겨요.
3. **기록:** 관찰값 / 들은 구간 / 내용과의 관계 / 다른 설명 가능성 / 판정 또는 보류 이유. 평가자 의견이 갈리면 수치로 승자를 정하지 않아요.

### 재현 기록

녹음마다 익명 녹음 번호, 파일 해시(SHA-256), 원고 버전, 분석 시작·끝 시각, 자른 여백, 코드 커밋(`profile.js`·`analysis.js`), 실행 명령, 녹음·재생 조건을 적어요. 녹음 파일 자체는 저장소에 올리지 않아요.

**이 시연이 보여 줄 수 없는 것:** 두 낭독은 여러 특성이 함께 바뀌어서 어느 특성이 인상을 만들었는지 나눌 수 없어요. 한 화자·5문장·평가자 2명으로 보편적인 따뜻함 효과나 측정의 타당성을 입증하지 못해요. GPT Q4가 낸 "20문장 × 2방식"은 첫 탐색 운영안일 뿐, 필요한 최소 표본이나 검증 완료 기준이 아니에요.

**공개할 것:** 미리 정한 5문장 전부(검출 실패·보류 문장 포함). 맞은 사례와 안 맞은 사례, 검출 실패와 판단 보류 사례를 모두 공개하고, 결과가 마음에 들지 않는다고 다른 녹음으로 바꾸지 않아요.
